## Safety Constraints

- DON'T infer permission to discard work or bypass safeguards from a general task request, tool access, or your own plan. Existing user instructions count when they clearly cover the target and consequence. Otherwise, defer that destructive step.
- DON'T remove or relocate a worktree, run `git reset --hard`, or delete files with `git clean` before verifying the target repository, absolute worktree path, and branch/HEAD. Scripts must use `git worktree list --porcelain -z` for worktree inventory.
- DON'T bypass worktree safeguards with `--force` (including repeated `--force`), `git worktree unlock`, or filesystem operations without authorization for the override and its consequences. This applies even on the first command attempt. Read the lock reason before unlocking; an absent reason does not establish that unlocking is safe.
- DON'T use `git worktree add -B` unless resetting the named branch to the selected commit is authorized; use `-b` for a new branch.
- DON'T remove a worktree until you have inspected its local state and verified preservation of needed tracked changes, untracked files, and ignored files outside that worktree. Keep needed commits, including detached commits, reachable through a retained branch or tag. A clean status is insufficient; ignored does not mean disposable. Discard only work covered by the user's authorization.
- DON'T delete worktree directories with filesystem commands or a file manager for routine cleanup; use `git worktree remove`. The main worktree is not a removable linked worktree.
- DON'T substitute filesystem relocation for `git worktree move` merely because Git refuses. That command cannot move the main worktree or worktrees containing submodules. An authorized filesystem relocation requires checking those constraints and preserving the complete worktree, including its `.git` file or directory. After moving the main worktree, run `git worktree repair` there; for moved linked worktrees, run it from the main worktree with their new absolute paths. If both moved, use the new main location and new linked paths. Verify reconnection before further work.
- DON'T apply ordinary worktree creation, relocation, or removal procedures to repositories with submodules without checking submodule-specific constraints and preserving needed work in each affected submodule. Git's submodule support is incomplete, and multiple worktrees of a superproject are discouraged; authorization alone does not resolve these limitations.
- DON'T prune worktree entries merely because their paths are missing. Establish that the worktrees were removed, rather than relocated or taken offline. Review `git worktree prune -n` with the same expiry options as the intended prune. Repair relocated worktrees instead; lock worktrees on removable or network storage before it goes offline.
- DON'T assume branches or repository configuration are isolated by worktree. Branch refs are shared; `HEAD` is worktree-specific. Resetting an attached branch moves that shared ref, although it does not update other worktrees' files. `git config --worktree` writes shared repository configuration when `extensions.worktreeConfig` is disabled.
- DON'T enable `extensions.worktreeConfig` without migrating existing `core.worktree` and `core.bare` settings from common configuration to the main worktree's `config.worktree`. With the extension enabled, do not share `core.worktree` or `core.bare=true`; share `core.sparseCheckout` only if every worktree uses sparse checkout.
- DON'T enable `extensions.worktreeConfig` or relative worktree paths without checking that every Git installation required to access the repository supports the resulting extensions; unsupported versions may refuse the repository.
- DON'T edit Git ref files or worktree administrative files directly; use Git commands. Resolve internal paths with `git rev-parse --git-path` from the verified target worktree.
